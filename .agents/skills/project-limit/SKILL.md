# Project Limit

在任何本機專案協助開發時，依下列四類規則約束行為。

## 1. 專案範圍限制

- 所有讀取、搜尋、建立、修改與執行指令，預設只能在目前專案根目錄及其子目錄內進行。
- 在本專案根目錄及其子目錄內執行的 `cd` 指令預設允許，不需另行確認；切換到專案根目錄之外仍受上述限制約束。
- 若任務確實需要讀取或寫入專案外資源，先說明需要存取的確切路徑、目的與影響，並取得使用者明確同意後才能繼續。

## 2. 敏感系統資訊與硬體健康

- 任何涉及硬體健康、磁碟狀態、系統診斷、網路設定、系統日誌、已安裝軟體、環境變數、憑證、帳號資訊或其他非專案資料的存取，都必須先取得使用者明確確認。
- 未取得確認時，提供安全的檢查建議或請使用者自行貼出必要的非敏感結果，不執行實際查詢。
- 永遠不得要求、輸出或儲存 API key、密碼、token、私鑰或其他憑證。

## 3. UTF-8 編碼規範

- 讀取、建立與修改文字檔時，預設使用 UTF-8 編碼。
- 修改既有檔案時，必須保留原始編碼與換行格式；若無法安全辨識，先詢問使用者，不可自行轉換編碼。
- 產生的程式碼、設定檔、Markdown 與腳本必須能在 UTF-8 環境正確顯示中文與其他 Unicode 字元。
- 不得因格式化、重寫或工具操作而造成亂碼、遺失非 ASCII 字元或整個檔案不必要的編碼變更。

## 4. 最小化與模組化修改

- 產生或修改程式碼時，優先採用模組化設計：清楚分離職責、使用小型可測試的函式或模組，避免把無關邏輯混入既有檔案。
- 僅修改完成目前任務所必須變動的最小區塊。
- 不得擅自重構、重新格式化、重新命名、搬移或改變其他無關程式碼。
- 若發現相鄰區域存在可改善之處，先說明建議，但不要自行修改。
- 每次進行檔案操作（建立、修改、刪除、搬移）前，先向使用者概略說明本次操作的摘要——預計動到哪些檔案、做什麼調整；說明後再執行。
- 每次修改後，清楚列出修改了哪些檔案及原因；有可用測試時，只執行與本次變更相關的測試。

## 5. 框架決策與重大異動

- 遇到框架層級的問題（技術選型、架構調整、資料流程與模組邊界設計等影響專案結構的決策）時，參照網路上的 grill-me（grill.me）模式：主動向使用者逐項提問、列出選項與影響，待使用者決策後再實作；不得擅自決定後直接動手。
- 發生重大框架異動時，必須同步更新 README.md 的相關章節（技術棧、資料流程、目錄結構、里程碑等），保持文件與實際狀態一致。
